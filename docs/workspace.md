# 워크스페이스 사용법

| 위치 | 책임 |
| --- | --- |
| `docs/` | 현재 합의한 방향·용어·범위·운영 규칙 |
| `research/` | 외부 사례, 출처, 비교와 열린 질문 |
| `packages/<name>/` | 지속적으로 사용할 앱·라이브러리·도구 |
| `experiments/<name>/` | 좁은 가설을 확인하는 프로토타입과 결과 |

이름은 짧은 영문 kebab-case, 문서 본문은 한국어를 기본으로 한다. 실제로 필요해진 폴더만 추가한다.

## 연구에서 구현까지

1. 작은 조사는 `research/<topic>.md`에서 시작한다. 자료가 많아지면 `<topic>/README.md`를 진입점으로 분리한다.
2. 실행 확인이 필요하면 `experiments/<name>/`을 만든다.
3. 중요한 선택이 확정되면 `docs/decisions/`에 근거를 남기고 관련 명세를 갱신한다.
4. 지속적으로 사용할 구현은 `packages/<name>/`에 둔다. 실험에서 옮길 때 원래 실험과 결정을 연결한다.

모든 변경이 이 단계를 거칠 필요는 없다. 단순한 수정은 바로 수행한다.

## 패키지 만들기

앱도 라이브러리도 우선 `packages/` 아래에 둔다. 독립 목적이나 실행·배포 단위가 있을 때 나누며, 미래 기능마다 빈 패키지를 만들지 않는다. 공통 코드는 실제 재사용이 생긴 뒤 추출한다.

각 패키지 README에는 목적, 현재 상태, 실행·검증 방법, 설정·데이터 위치, 의존 패키지를 적는다. 내부 소스·테스트·manifest 구성은 선정한 언어와 도구의 관례를 따른다. 다른 패키지의 내부 파일을 임의로 참조하기보다 공개 경계를 정한다.

루트에 특정 언어의 workspace 설정이 없어도 모노레포로 운영할 수 있다. 통합 빌드 도구는 실제 필요와 스택을 확인한 뒤 선택한다.

## 문서와 데이터

같은 내용을 여러 문서에서 관리하지 않고 링크한다. 현재 제품 합의는 `product.md`에 모으고, 커지면 주제별로 분리한다. 대화 전문을 모두 정리할 의무는 없다. 이후 판단에 필요한 결정·근거·미결정 사항을 남긴다.

실제 개인 자료는 저장소 밖에 둔다. 재현용 가상 샘플은 패키지나 실험의 `fixtures/`에 둔다.
