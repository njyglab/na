## 이어갈 질문

- Memos의 실제 메모 단위·본문 표현·날짜·수정·관계는 어떻게 구성되어 있는가? na의 제목 없는 Block과 어느 부분이 맞고 다른가?
- Bullet Journal의 기록 동작을 디지털 Bullet에 어떻게 대응시킬 것인가? 항목을 별도 객체로 둘지 본문 안에 둘지, 상태·중첩·이동·참조 요구를 사례로 판단한다.
- Daily log는 저장 객체인가 날짜별 조회인가? Block의 작성 시각·기록 대상 날짜·수정 시각과 정렬을 어떻게 구별할 것인가?
- 파일 기반과 SQL 기반 중 어떤 저장 방식이 실제 사용·수정·검색·내보내기·백업·복원에 맞는가? UI 모델을 곧바로 스키마로 확정하지 않는다.
- 원본 기록과 파생 정리, 수정 이력, 댓글과 실패 보완의 관계를 어느 정도까지 첫 MVP에 담을 것인가?

## 조사 방식

Memos와 Anchor의 공식 문서·실제 소스부터 확인한다. 필요하면 다른 사례를 추가하되 제품 수를 늘리는 것보다 구체적인 사용 장면과 데이터 동작 비교를 우선한다. 출처·확인 버전 또는 커밋·관측 사실·na에 대한 해석·미확인 사항을 구별한다.

산출물 목표는 사례 비교 → 사용자 동작과 용어 정리 → 도메인 후보 → 데이터 모델과 저장 방식의 대안 비교다. 처음부터 ORM·DB·에디터 라이브러리를 확정하지 않는다. 애매한 사용자 용어는 되짚어 확인한다.

## 유지할 경계

- 사람이 쓰는 daily log가 최우선. 캘린더와 하루 Feed, 제목 없는 Block, BuJo 성격의 Bullet이 중심이다.
- Card/Zettel과 실행 자원의 명칭·형태는 미정이며 첫 MVP에서 보류할 수 있다.
- 첫 MVP는 온라인 전용·개인 사용자. 서버 영속 데이터가 원본이며 클라이언트 캐시·오프라인 동기화는 후속 범위다.
- 다중 계정·공유는 미래 가능성을 고려하되 지금 전체 기능을 구현하지 않는다.
- TypeScript·pnpm·Node.js, Next.js·React, Turborepo 채택. 집 서버 Docker·Tailscale 운영, 소스·이미지 공개, GHCR 사용.
- ESLint·Prettier·Vitest·Playwright 등 상세 도구와 SDLC 자동화는 기준안이며 설치·실행되지 않았다.

## 남은 비모델링 결정

공개 라이선스, 정확한 도구 버전, 서버 Compose 설치 방식, HTTPS·앱 인증, 저장 방식에 맞는 백업·복구 정책. 연구와 무관한 설치 작업부터 시작하지 않는다.
