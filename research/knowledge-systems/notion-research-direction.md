# Notion을 중심으로 지식·업무 시스템을 분해하는 연구

작성: 2026-09-27. 상태: 공식 자료에 근거한 초기 연구 설계. 제품 실행·내부 구현 분석·이관 검증 전.

## 사용자 의도와 범위

PKM뿐 아니라 협업 SaaS, 기업 KMS, 온톨로지 시스템까지 포함해 각 도구의 위상과 성질을 파악한다. 겹치는 기능을 내가 통제하고 재구성할 수 있는 단위로 분해하는 것이 목적이다. 제품 수나 기능 수를 늘리는 것 자체를 목표로 하지 않는다.

중심 사례는 Notion이다. Tana, Linear, ClickUp, AFFiNE, AppFlowy, SiYuan, Docmost를 비교 대상으로 추가한다. 추가 제안은 [초기 지형도](synthesis/software-landscape.md)에서 별도로 관리한다. Darwin·Luhmann의 실제 인스턴스 탐구는 보존하며 이번 연구가 그 결과를 대체하지 않는다. na의 현재 MVP나 저장 기술을 변경하는 결정은 아니다.

## 핵심 질문

> 문서·데이터·업무 도구의 반복되는 기능을 어떤 책임과 연산으로 분해하면, 의미와 작업 흐름을 보존하면서 구현·운영·표시 도구를 바꿀 수 있는가?

‘기술적 환원’은 세 가지 산출물을 구별한다.

1. **제품의 의미 모델**: 사용자가 무엇을 만들고, 가리키고, 수정하는가?
2. **기능을 성립시키는 책임과 계약**: 식별·저장·관계·질의·표시·행동·권한·복구는 어떻게 나뉘는가?
3. **구현 선택지**: 파일/SQL/그래프, 에디터, 동기화 방식 등을 어떤 근거로 선택할 것인가?

공개 API는 외부 계약이며 내부 DB 스키마나 실행 구조의 증거와 동일하지 않다. Notion의 실제 내부 스택, 대안의 소스 구현, 우리가 설계할 최소 구현을 따로 기록한다. 이번에는 1과 2를 연구하고 3은 필요한 검증 질문만 남긴다.

## Notion의 에센셜 — 작업 가설

**주소를 가진 내용 조각과 속성을 가진 문서를, 관계·질의·여러 뷰·공동 작업으로 조합하는 작업 환경.**

‘블록 기반 지식 운영 시스템’은 유용한 상위 설명이다. 다만 블록 편집만으로 설명하면 페이지가 구조화된 데이터 항목이면서 본문을 갖는다는 결합을 놓친다. [Notion 사례](cases/notion.md)의 공개 계약에서 확인한 단위부터 출발한다.

## 분해할 책임 — 확정 아키텍처가 아닌 비교 렌즈

| 책임 | 무엇을 보존·조작하는가? | 핵심 질문 |
|---|---|---|
| 식별과 수명 | 안정 ID, 이름, 위치, 이동·삭제·복구 | 이름이나 부모를 바꾸어도 같은 대상인가? |
| 내용과 구성 | 텍스트·블록·첨부·순서·중첩 | 내용의 단위와 조작 단위는 같은가? |
| 타입과 속성 | 스키마, 값, 선택적 제약 | 자유 기록을 언제 구조화하며 변경 비용은? |
| 관계와 참조 | 포함·인용·재사용·업무 의존성 | 링크 종류를 하나로 합치면 무엇을 잃는가? |
| 질의와 계산 | 필터·정렬·집계·파생값 | 저장값과 재생성 가능한 결과를 구별하는가? |
| 뷰와 상호작용 | 표·보드·타임라인·문서·캔버스 | 같은 데이터를 복제하지 않고 다시 표현하는가? |
| 행동과 규칙 | 상태 전이·버튼·자동화·외부 부작용 | 상태 필드와 실행 가능한 업무 규칙은 어떻게 다른가? |
| 협업과 거버넌스 | 주체·권한·댓글·이력·검토 책임 | 참조·검색·파생값에서도 접근 경계가 유지되는가? |
| 보존과 교체 | 내보내기·가져오기·백업·복원·API | 텍스트뿐 아니라 관계와 규칙을 다시 구성할 수 있는가? |

권한·이력·복구는 전체에 걸친 책임이다. 이 표의 행마다 서비스나 패키지를 만들 필요는 없다. AI는 각 책임의 입력·제안·질의 보조로 관찰하되, 출처·사용자 수정·오류 회복을 따로 확인한다.

## ‘통제 가능’의 평가 기준

소스 공개, 로컬 저장, 자체 호스팅, 데이터 이식성, 동작 변경 가능성은 서로 다른 축이다. 공개 저장소가 있어도 필요한 기능의 라이선스·서비스 의존·실행 경계는 판본별로 확인해야 한다.

| 축 | 완료 증거 |
|---|---|
| 읽을 수 있음 | 제품 밖에서 원본·첨부·식별자를 해석 |
| 표현할 수 있음 | 속성·관계·순서·시간·출처를 모호하지 않게 기술 |
| 조작할 수 있음 | UI 밖에서도 지원되는 연산과 오류 상태 확인 |
| 교체할 수 있음 | 표시기·검색기 교체 후 같은 대상을 가리킴 |
| 재구성할 수 있음 | 내보내기 → 다른 표현 → 복원 뒤 핵심 의미 비교 |
| 유지할 수 있음 | 스키마 변경·잘못된 자동화·누락·복구 비용 측정 |

종합 점수 대신 각 축에 ‘문서 확인 / 실행 확인 / 미확인 / 범위 밖’을 부여한다. 인간에게 유용한지는 별도로 관찰한다. 통제력이 높다는 이유만으로 입력·유지 부담이 작다고 간주하지 않는다.

## 조사 순서와 산출물

1. **Notion의 단위·연산 지도**: page/block/data source/database/view의 식별·포함·참조·속성 관계를 구별한다. API 버전을 고정하고 UI와 대조한다. 내부 구현과 혼동하지 않는다.
2. **작은 가상 인스턴스 추적**: 아래 장면을 UI 동작·API 표현·내보내기로 따라간다. 예상과 실제를 구분한다.
3. **대조 사례로 가설 수정**: Tana(점진적 타입 부여), Airtable/Coda(구조화 데이터와 계산), Linear/ClickUp(업무 의미), AFFiNE/SiYuan/AppFlowy/Docmost(각기 다른 통제·구성 경계)를 질문별로 선택한다.
4. **최소 책임과 제거 비용**: 각 기능을 빼거나 다른 도구로 옮겼을 때 무엇을 잃는지 기록한다. 공통점만 남겨 모든 사례의 고유 의미를 지우지 않는다.
5. **기업·의미 시스템으로 확장**: KMS의 관리 책임과 온톨로지의 의미·추론·실행 책임을 구분한다. 더 복잡한 시스템을 자동으로 더 좋은 상위 단계로 평가하지 않는다.

완료 단위: 한 장면에 대해 ‘보존할 데이터 / 연산 / 규칙 / 뷰 / 권한 / 복원 한계’를 근거와 함께 설명하고, 줄여도 되는 부분과 아직 줄일 수 없는 부분을 제시한다. 소프트웨어를 전부 설치하는 것은 선행 조건이 아니다.

## 가상 인스턴스와 제거 실험 후보

가상 자료·메모·질문을 소수 만들고 자료↔메모↔질문을 연결한다. 중요한 장면은 다음과 같다.

- 같은 항목을 문서·표·보드에서 열고 수정한다: 같은 대상의 표현인가, 복제인가?
- 제목·위치·속성 타입을 바꾼다: ID·참조·질의는 어떻게 변하는가?
- 원문 내용을 고치거나 관계 대상을 삭제한다: 과거 해석·파생값·복구는?
- 일부만 공유한다: 숨긴 대상에 대한 링크·집계가 어떤 정보를 노출하는가?
- 내보내고 다시 구성한다: 본문·스키마·관계·뷰·계산·권한 중 무엇이 남는가?
- 보드·자동화·AI·협업 기능을 하나씩 빼본다: 작업이 불가능해지는가, 수작업으로 대체되는가, 유지 비용이 이동하는가?

실험은 아직 실행하지 않았다. 최종 산출물은 ‘최소 기능 목록’보다 **의미를 보존하는 최소 계약과 비용 장부**를 목표로 한다.
