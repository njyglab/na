# 시스템을 설계하며 풀어야 할 문제들

시작·갱신: 2026-09-26. 상태: 문제 장부의 첫 버전. 아래의 설계 후보는 채택된 아키텍처나 구현 요구사항이 아니다. 현재 범위는 [제품 문서](../docs/product.md)를 따른다.

## 출발점과 근거

사용자는 메모를 원 소스에 물리적·디지털적으로 부착된 것으로만 정의해야 하는지 고민해왔다. 이번 대화에서는 **내가 관리하는 독립 메모에서 원 소스를 느슨하게 참조하는 방식도 가능하다**는 잠정적인 타협에 도달했다. 원본 위에 주석을 표시하는 방식도 여전히 가능하며, 어느 방식에서든 주소체계를 다루어야 한다.

따라서 다음 세 질문을 분리해 연구한다. 메모는 어디에 보존되는가? 무엇을 어떤 단서로 가리키는가? 읽을 때 어디에 표시되는가? 독립 메모도 원본 위에 표시할 수 있고, 원본 위에 보이는 주석도 별도로 보존할 수 있다. 이는 설계상의 구별이며 현재 구현의 능력이 아니다.

이 문서의 근거는 다음과 같다.

- **사용자 관점**: 2026-09-26 이 프로젝트 대화에서 직접 밝힌 문제와 잠정적 타협. 특정 저장 스키마의 승인을 뜻하지 않는다.
- **사용자 제공 외부 대화 요약**: 같은 날 전달받은 「공부 시스템화에서 ‘그 때 그거’ 소멸 체계까지」. 원 대화 날짜·전체 원문·외부 근거는 미확인이다. 아래 후보들의 출처이며 검증된 기술·역사 사실로 취급하지 않는다.
- **프로젝트 연구**: [Darwin 표본 분석](knowledge-systems/synthesis/darwin-note-patterns.md), 특히 B153 → RN130·132의 재참조. 느슨한 참조의 실제 사례지만 오늘날 시스템의 효과나 충분성을 입증하지 않는다.

## DP02–DP04: 독립 메모와 주소체계

‘느슨하다’는 것은 메모가 원본의 저장·표시 방식에 전적으로 종속되지 않을 수 있다는 뜻으로 사용한다. 대상을 모호하게 가리켜도 항상 괜찮다는 뜻은 아니다. 빠르게 남길 때 허용할 불완전함과, 인용·검증할 때 필요한 정밀도는 다를 수 있다.

주소 문제를 검토하기 위한 작업 어휘를 둔다. 아직 필수 필드나 객체 모델은 아니다.

| 구별 | 질문 | 예시·주의 |
|---|---|---|
| 대상 식별 | 무엇을 가리키는가? | 저작, 특정 문서, 내 메모를 구별. URL 하나가 모든 정체성을 설명하지는 않음 |
| 판본·상태 | 어떤 시점·버전의 대상인가? | 읽었던 PDF와 수정된 PDF, 원노트와 편집 전사본 |
| 접근 위치 | 현재 어디에서 열 수 있는가? | 웹 주소·파일 경로·종이책 소장 위치. 위치가 달라도 같은 자료일 수 있음 |
| 부분 지시 | 대상의 어느 부분인가? | 페이지·문단·인용문·영상 시각. 한 생각이 여러 부분을 가리킬 수도 있음 |
| 발견 단서 | 주소를 모를 때 무엇으로 찾는가? | 읽은 날짜·주제·인물·관련 메모·작업 맥락 |
| 해석·확인 | 단서가 실제 어느 대상으로 이어지는가? | 후보가 여럿이거나 접근할 수 없을 수 있음. 검색 결과와 확인된 참조를 구별 |

Darwin 연구에서는 RN 원노트 쪽수, 1987년 판본 인쇄 쪽수, PDF 디지털 쪽수가 공존했다. 예컨대 보고서의 RN5e–8e 표본은 인쇄 21–22쪽, PDF 31–32쪽에 걸친다. ‘31쪽’만 저장하면 이 구별이 사라진다. 반면 다윈 자신이 쓴 노트명+쪽수 참조는 당시의 자기 기록으로 돌아갈 단서였다. 필요한 주소 정밀도는 사용 맥락에 따라 달라진다.

앞으로 확인할 쟁점:

- 출처를 아직 모르는 메모, 소스 전체를 가리키는 메모, 여러 소스를 비교하는 메모를 어떻게 자연스럽게 남길 수 있는가?
- 최신 원문을 따라가는 참조와 읽었던 상태를 재현하는 참조를 어떻게 구별하는가?
- 인용문·주변 문맥·쪽수 등을 함께 남기면 주소가 깨졌을 때 얼마나 복구할 수 있는가? 같은 문구가 반복되면 어떻게 확인하는가?
- 이동·소실·권한 부족·복수 후보를 구별해서 사용자에게 알릴 필요가 있는가? 자동 복구가 잘못된 곳을 선택하면 어떻게 바로잡는가?
- 원문 복제 없이 충분한 경우와 사본이 필요한 경우를 어떻게 나누는가? 보존 가능 범위·접근 권한·용량·수작업 비용도 함께 평가해야 한다.

## DP05: ‘그때 그거’를 줄인다는 것

외부 요약의 ‘주소를 없앤다’는 표현은 **사용자가 정확한 저장 위치를 기억해야 하는 부담을 줄인다**는 목표로 해석한다. 시스템 내부에서 대상을 식별하고 찾아갈 책임까지 사라지는 것은 아니다. 재탐색 실패에는 좌표 외에도 기록 누락, 기억의 모호함, 접근 불가, 문맥 손실이 관여할 수 있다.

내용·개념·시간·관계·출처·메모를 함께 쓰는 검색은 후보이다. 후보를 발견하는 일과 그것이 의도한 자료인지 확인하는 일을 분리해 관찰한다. 성공 기준에는 찾는 시간뿐 아니라 잘못 고른 횟수, 확인에 필요한 문맥, 작업 재개 가능성, 평소 기록·관리 부담도 포함한다. 목표는 완전한 소멸보다 실제 실패와 부담의 감소다.

## 외부 대화에서 가져온 설계 후보와 남은 검증

| 제안 | 대응 문제 | 아직 결정하지 않은 부분 |
|---|---|---|
| Capture → Normalize → Link → Surface, 정규화 코드를 직접 소유 | DP01·08·10 | 정규화할 범위·시점과 유지 비용. 저장 전에 모든 자료를 변환해야 하는지는 별도 문제 |
| 메모를 횡단 관심사로 보고 `anchor + body + author + visibility` 계약 사용 | DP02·03·09 | 출처 없는 기록·복수 참조·불완전한 anchor를 포함할 수 있는가? 이 필드를 필수로 요구할 이유가 있는가? |
| L0 휘발 / L1 작업 / L2 정본 / L3 내구 / L4 라이브 / L5 색인 | DP04·07 | 서로 다른 책임을 구별하는 후보. 실제 저장소 수·배치·동기화 방식은 미정 |
| ‘L2 단방향’, ‘L5 폐기 가능’, ‘anchor는 L2를 가리킴’ | DP03·04·07 | 단방향의 정확한 의미, 색인 재생성에 필요한 원자료, 외부 원본을 복제하지 않는 참조와의 양립 가능성 |
| 렌더러를 선택하거나, 메모를 바깥에 두거나, 직접 구현 | DP02·06 | 자료별 실제 지원 범위와 읽기 흐름의 비용. 자체 렌더러의 필요성은 미검증 |
| 인지 표면 → 라우터 → 저장, 지연적 캐시·다중 색인 | DP05·07·10 | 라우터가 하는 일, 오답·피드백·캐시 갱신·대체 경로. 학습 기반 방식이 필요한지도 미정 |
| 1주일 최소 PoC | DP05·08 | 실험할 실패 장면과 비교 기준부터 선택. 기간·구현·착수는 미합의 |

외부 요약의 저장 속성도 평가 질문으로 보존한다. 지속성, 가용성, 지연, 비용, 충실성, 불변성, 검증성, 주권, 복구성, 색인성과 신선도, 재현성, 이식성, 감사가능성, 회복탄력성, TCO를 검토하되, 서로 독립적인 축인지와 측정 방법은 미정이다. 이를 한 번에 최대화하는 요구사항으로 만들지 않는다.

인쇄 시대의 여백·주석본·색인과 디지털 메모의 연속성, 개인 연결망의 비용을 제도가 흡수하거나 개인에게 전가한다는 설명은 후속 연구 가설로 남긴다. 현재 자료만으로 ‘기술이 아니라 제도 문제’라고 확정하지 않는다. 공개성·도달성·귀속성·혼합성이라는 외부 요약의 어휘도 정의와 사례가 더 필요하다.

## 다음에 작게 확인할 장면

아래는 실험 후보이며 아직 실행하지 않았다. 하나를 선택해 기록 부담과 다시 찾는 과정을 관찰한다.

1. PDF의 한 대목을 별도 메모에서 참조한 뒤, 파일명이나 뷰어를 바꿔도 그 대목과 생각을 다시 찾을 수 있는지 확인한다(DP02·03·06).
2. 원문이 바뀌거나 열리지 않는 상황에서 URL만 남긴 경우와 인용문·판본 단서를 함께 남긴 경우를 비교한다(DP03·04).
3. 주소를 숨기고 ‘언제 어떤 맥락에서 읽었는가’만으로 찾는다. 후보 발견과 정답 확인 시간을 따로 기록한다(DP05).

## 운영 규칙과 연결

- 새 문제는 실패 장면, 근거, 남은 질문을 함께 추가한다. 기존 ID는 유지하고 합치거나 닫으면 이유와 이동 위치를 남긴다.
- 사용자 경험, 문헌 관찰, 우리의 해석, 구현 후보, 실험 결과를 구별한다. 검증된 결과가 생기면 해당 문제에 날짜·근거·상태 변화를 기록한다.
- 사례에서 무엇이 일어나는지는 [지식 시스템 연구 질문](knowledge-systems/questions/README.md)에, na에서 무엇을 풀어야 하는지는 이 문서에 둔다. [Source·Citation·Provenance](knowledge-systems/questions/epistemic-lineage.md) 구별도 이어 사용한다.
- 구체적인 합의가 이루어지면 [결정 기록](../docs/decisions/README.md)과 필요한 제품 문서에 반영하고 여기서 연결한다. 이 장부의 문제·후보를 자동으로 기능 목록이나 개발 할 일로 옮기지 않는다.
